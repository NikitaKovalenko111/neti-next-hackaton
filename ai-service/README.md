# AI service

Для совместного запуска с backend используйте `docker compose up --build -d` из корня репозитория. Общая конфигурация и адреса описаны в [README проекта](../README.md). Ниже описаны самостоятельные способы запуска AI-сервиса.

FastAPI-сервис получает задачи из RabbitMQ, вызывает Qwen3 через OpenRouter и публикует ответ обратно в очередь. Код разделён на транспорт `app/transport`, бизнес-логику `app/services` и HTTP-клиент модели `app/clients`.

AI-сервис передаёт Qwen инструменты поиска по кампусу и материальной поддержке. Модель может сделать несколько вызовов подряд, прочитать результаты и использовать их в ответе. Go передаёт в задаче RabbitMQ текущее сообщение, последние пять предыдущих сообщений пользователя с доступными ответами и аннотацию чата.

## Запуск с существующим RabbitMQ

Из каталога `ai-service` (Python 3.12+):

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
```

В `.env` задайте `OPENROUTER_API_KEY`, параметры PostgreSQL из `RAG_POSTGRES_*` и тот же брокер RabbitMQ и имена очередей, которые использует backend. После подготовки схемы `rag` выполните:

```sh
python -m app.index_campus
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

`GET http://localhost:8000/health` возвращает `200`, если worker подключён к RabbitMQ и OpenRouter принимает API-ключ; иначе `503`. Запросы пользователей поступают через RabbitMQ, отдельного HTTP endpoint для генерации нет.

## Автономный запуск через Docker Compose

```sh
docker compose up --build -d
docker compose logs -f rag-index ai-service
```

Compose из каталога `ai-service` запускает PostgreSQL с pgvector, RabbitMQ и AI-сервис.
Укажите `OPENROUTER_API_KEY` в `ai-service/.env` перед запуском. Воркер ждёт завершения
`rag-index`. Сервисы доступны на `localhost:8000` (AI) и `localhost:5672` (RabbitMQ).

Если backend уже использует свой RabbitMQ, используйте первый способ запуска или подключите контейнер AI-сервиса к тому же брокеру. Два разных брокера не обмениваются этими очередями автоматически.

## Настройки

Все настройки можно передать через окружение или `.env`:

| Переменная | Значение по умолчанию |
| --- | --- |
| `RABBITMQ_URL` | `amqp://guest:guest@localhost:5672/` |
| `RABBITMQ_QUEUE` | `agent_requests` |
| `RABBITMQ_RESPONSE_QUEUE` | `agent_responses` |
| `OPENROUTER_API_KEY` | Задаётся в `.env` |
| `OPENROUTER_BASE_URL` | `https://openrouter.ai/api/v1/` |
| `OPENROUTER_MODEL` | `qwen/qwen3-30b-a3b-instruct-2507` |
| `OPENROUTER_EMBEDDING_MODEL` | `baai/bge-m3` |
| `OPENROUTER_TIMEOUT_SECONDS` | `180` |
| `OPENROUTER_MAX_TOKENS` | `1024` |
| `RETRY_DELAY_SECONDS` | `5` |
| `RESPONSE_CACHE_SIZE` | `128` |

В Compose адреса сервисов заданы внутренними именами контейнеров; `.env` позволяет изменить имена очередей, модель и таймаут. Для изменения остальных настроек контейнера добавьте соответствующие переменные в `environment` сервиса.

## Контракт сообщений

Вход из `agent_requests` соответствует контракту Go backend:

```json
{
  "message_id": "11111111-1111-4111-8111-111111111111",
  "chat_id": "22222222-2222-4222-8222-222222222222",
  "user_id": "33333333-3333-4333-8333-333333333333",
  "message": "В Уфе",
  "attachments": [],
  "conversation": {
    "history_summary": "Пользователь хочет найти нужную аудиторию.",
    "recent_turns": [
      {
        "user_message": "Где моя аудитория?",
        "assistant_message": "В каком городе находится ваш корпус?"
      }
    ]
  }
}
```

Выход в `agent_responses`:

```json
{
  "request_message_id": "11111111-1111-4111-8111-111111111111",
  "blocks": [
    {
      "type": "text",
      "message": "Уточните, пожалуйста, название корпуса и номер аудитории."
    }
  ],
  "history_summary": "Пользователь уточняет расположение нужной аудитории."
}
```

Если во входном AMQP-сообщении задан `reply_to`, ответ отправляется в указанную очередь; иначе используется `RABBITMQ_RESPONSE_QUEUE`. AMQP `correlation_id` ответа равен исходному `message_id`. Сейчас AI-сервис формирует только текстовые блоки.

Обе основные очереди объявляются как durable. Ответ публикуется как persistent-сообщение с ожиданием подтверждения брокера; только после этого подтверждается исходная задача. Предзагрузка ограничена одной задачей на worker.

Go сохраняет новую аннотацию после записи ответа и передаёт её в следующих задачах.
Аннотация покрывает диалог до исходного сообщения ответа включительно. Если к моменту
постановки задачи появились старые сообщения, ещё не учтённые в аннотации, Go передаёт
их в `conversation.older_turns`. Воркер сворачивает их частями перед ответом. Аннотация
передаётся через очередь ответа и хранится в схеме Go. Пользователь получает текстовые блоки по WebSocket.

Некорректные сообщения отклоняются без повторной постановки. При ошибке генерации или публикации задача возвращается в очередь после паузы. После потери соединения используется переподключение aio-pika. Во время остановки неподтверждённые задачи остаются у брокера для повторной доставки.

Успешные ответы кэшируются по `message_id` в ограниченном кэше в памяти. Это уменьшает повторные генерации, в том числе после ошибки публикации. Кэш теряется при перезапуске и не разделяется между процессами: доставка остаётся at-least-once, а backend сохраняет ответы идемпотентно по `request_message_id`.

## Справочник кампуса

Миграции в `app/migrations` загружают `all.json` в схему `rag` под отдельной ролью PostgreSQL. Таблицы хранят подразделения, корпуса, общежития, жилищные сводки, ссылки на фотографии и источники. Спорные адреса сохраняются отдельно. Векторный поиск работает по текстам карточек и жилищных сводок, а для фотографий хранится статус привязки к объекту.

Из корня репозитория запустите импорт и построение 1024-мерных эмбеддингов `baai/bge-m3` через OpenRouter:

```sh
docker compose up -d --build rag-index
docker compose logs -f rag-index
```

Повторный запуск обрабатывает только карточки без актуального вектора для выбранной модели. При смене модели сначала дождитесь завершения `rag-index`, затем пересоздайте `ai-service`. Индекс хранит эмбеддинги отдельно для каждой модели. Векторный поиск с фильтром по филиалу и типу карточки:

```sh
docker compose run --rm rag-index python -m app.index_campus \
  --query 'Где находится общежитие в Нефтекамске?' \
  --branch neftekamsk --kind dormitory
```

Для импорта только в PostgreSQL поднимите `postgres-init` из корня и выполните `python -m app.index_campus --import-only` из `ai-service` с учётными данными роли `rag_app`. Настройки локального подключения указаны в `.env.example`.

При запуске Compose задача `campus-photos` скачивает JPEG по ссылкам из справочника,
загружает их в бакет MinIO и записывает ключи объектов в PostgreSQL. Повторный
запуск использует уже загруженные объекты. Если источник недоступен, задача пишет
предупреждение и продолжает обрабатывать остальные фотографии.

При запросе фотографии агент выбирает доступный снимок из результата `list_photos`
и возвращает его блоком `attachments`. Go добавляет подписанный URL перед отправкой
через WebSocket или при чтении истории.

## Архив данных УУНиТ

Снимок от 21 ноября 2026 года содержит структурированные записи и краткие аннотации
с URL источников. При запуске `rag-index` миграции загружают записи в PostgreSQL,
а тексты аннотаций индексируются через OpenRouter и pgvector. Оригиналы документов
и служебные пути архива в репозиторий не входят.

- `search_university_records` ищет точные сведения по коду направления, филиалу и категории.
  `get_university_record` возвращает полную карточку со ссылками на источники.
- Отдельные инструменты подбирают варианты поступления, проверяют льготы и медосмотр,
  ищут учебные планы, контакты, даты приёма, графики заселения, стипендии, документы
  и сведения о доступности корпусов. [Сценарии и параметры](tools/README.md).
- `search_university_documents` ищет по смыслу аннотации, правила и даты.
- Стоимость, вступительные испытания и проходные баллы относятся к кампании 2026 года.
  Планы без даты остаются недатированными. Аннотации к прошлым кампаниям указывают свой период.
  У части сканов есть только карточка и ссылка на оригинал.

[Подготовленный JSON](app/migrations/university_knowledge.json)

Миграция `008_university_full_seed` загружает дополнение из архива от 21 ноября 2026 года.
Справочники обновляются по существующим идентификаторам. При сравнении использованы ключи
предметной области, ссылки и реквизиты приказов. Для сводок дополнительно проверялось совпадение
файлов и извлечённого текста. У сканов без надёжного текстового слоя сохраняются карточки и
ссылки на оригиналы. Отобранные фотографии загружаются в MinIO через `campus-photos`.
Эмбеддинги новых сводок рассчитывает `rag-index`.

## Материальная поддержка

Задача `rag-index` импортирует `material_support.json` вместе со справочником кампуса. В PostgreSQL есть отдельные таблицы программ, оснований, обязательных документов, каналов подачи и источников. В `rag.support_ground_details` доступны суммы и коэффициенты, периодичность, общий срок подачи, особый срок с событием отсчёта, документы и страницы нормативного источника.

Посмотреть основание и основной канал подачи для нужного филиала можно обычным SQL-запросом через CLI. Запрос выполняется без обращения к OpenRouter.

```sh
docker compose run --rm --no-deps rag-index python -m app.index_campus \
  --ground death_of_close_relative --branch ufa
```

В pgvector сохраняются только заголовок, короткое описание и пояснения к основанию. По свободному вопросу поиск сначала подбирает основания по смыслу, затем читает точные сведения из PostgreSQL. Сходство текста служит для подбора кандидатов. Решение о помощи принимает комиссия.

```sh
docker compose run --rm --no-deps rag-index python -m app.index_campus \
  --support-query 'нужны деньги на лекарства' --branch birsk
```

В одном ответе агент выполняет до четырёх раундов поиска и восьми вызовов. После лимита модель формирует ответ из собранных данных. [Каталог инструментов, параметры и примеры вызовов](tools/README.md).

## Проверка

```sh
ruff check .
ruff format --check .
pytest -q
```

Обычные тесты используют тестовые HTTP-ответы OpenRouter и проверяют контракт блоков, обработку ошибок, повторные доставки, порядок publish/ack и lifecycle FastAPI. Они используют локальные заглушки HTTP.

Для интеграционного теста с настоящим RabbitMQ:

```sh
TEST_RABBITMQ_URL='amqp://university:university@localhost:5672/' \
  pytest -q -m integration
```

Тест создаёт отдельные временные очереди и удаляет их после проверки. RabbitMQ настоящий, а ответ OpenRouter заменён тестовым. Без `TEST_RABBITMQ_URL` интеграционный тест пропускается.
